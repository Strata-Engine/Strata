# Finite hand-tunable maps (Timberborn) and authored voxel assets/levels (Teardown): what an engine must support

Research date: 2026-11-11. Engine context assumed: 32³ voxel chunks, real-time fluid sim that lets lakes drain when carved, block registry, Vulkan renderer; no save format, no asset import, no editor yet.

## Q1. Timberborn: map sizes, editor, terrain representation, water model, cycles, gameplay needs, community generators

### Takeaway
Timberborn maps are small bounded grids (official maps 50×50 up to 256×256; editor terrain capped at 16 blocks, 22 in-game), authored in the shipped Map Editor and saved as `.timber` ZIP+JSON. Water/badwater is a cell-based volumetric sim with point sources rated in m³/s and map edges acting as drains; since Update 6 (Oct 2024) water is fully 3D (flows over buildings) and since Update 7 terrain is true 3D (blocks on any solid surface, overhangs up to 3 blocks). Mechanistry has shipped no official random-map generator; procedural maps come from community mods (RTB TimberbornTerrainGenerator using FastNoiseLite, mrCurry90 ExtraTerrainTools heightmap generator).

### Cited Findings

**Map sizes**
- Official map list with sizes: Lakes 256×256, Plains 256×256, Waterfalls 128×128, Canyon 128×128, Cliffside 100×50, Craters 192×192, Helix Mountain 256×256, Hollows 192×192, Meander 128×128, Mountain Range 256×150 (was 196×196 in early EA; rebuilt in Update 5), Terraces 256×256, Thousand Islands 256×256, Beaverome 192×192, Diorama 50×50, Nomads 256×256, Oasis 256×256, Pillars 192×192, Pressure 256×256, Spillage 256×150. Page warns "Very large maps contribute to performance issues." — [Timberborn wiki.gg: Maps](https://timberborn.wiki.gg/wiki/Maps)
- A third-party guide reports the editor's New Map dialog accepts a minimum of 4 and a maximum of 256 per axis (not an official source). — [Steam guide (via search)](https://steamcommunity.com/sharedfiles/filedetails/comments/3413377775)
- Community mods raise the size/height caps; mod author notes a separate mod for raising the height limit and that players must also install it or the map crashes. — [Steam Workshop comments](https://steamcommunity.com/sharedfiles/filedetails/comments/3422772243)
- Heightmap import is a still-open player feature request, not a shipped feature. — [featureupvote: Heightmap world generation](https://timberborn.featureupvote.com/suggestions/273959/heightmap-world-generation)

**Height limits and terrain representation**
- "During map creation ground elevation is limited to 16 tiles"; in-game the total is 22 tiles, 11 of which are reserved for vertical building (stacking). Terrain can be reshaped "within the map's initial horizontal size" until hitting "the indestructible layer at the bottom or the highest possible ground elevation level" (exact bottom layer not stated). Terrain Blocks built by beavers from Dirt behave as natural terrain for irrigation, water physics, plant growth and ground-only buildings. — [wiki.gg: Terraforming](https://timberborn.wiki.gg/wiki/Terraforming)
- Map Editor page: maximum terrain height 16 blocks; editor adds trees, bushes, fluid and metal sources; map-specific options menu; top-right controls for season, fluid simulation and visibility; editor shipped at Early Access launch. — [wiki.gg: Map Editor](https://timberborn.wiki.gg/wiki/Map_Editor)
- Update 6 "Wonders of Water" (released 10 Oct 2024): new 3D water physics replacing the earlier "2.5-dimensional" system; water and badwater flow over buildings enabling aqueducts, underwater tunnels, underwater cities; new Overhangs incl. natural overhangs placeable in the map editor; official mod support + Steam Workshop; Cliffside added as a diorama-like map; existing maps reworked for 3D water. EA launch was 15 Sep 2021; >1M copies. — [Mechanistry press: Update 6](https://mechanistry.com/press/wonders-of-water-timberborn-update-6-adds-3d-water-physics-new-skyward-engineering-and-official-mod-support); [SteamDB patchnotes](https://steamdb.info/patchnotes/15964785)
- Update 7 (Ziplines & Tubeways): "While the in-game terrain has always been made of little 3D cubes, you could only place them one atop another. With Update 7, terrain blocks go on all Solid surfaces - roofs, platforms, and overhangs." Beavers can build overhanging terrain up to three blocks to the side; Natural Overhangs replaced by regular terrain blocks in game and editor; editor gained an overhang sculpting tool and a layer tool; relative terrain brush greys out tiles outside the map limit. — [Mechanistry press: Update 7](https://mechanistry.com/press/ziplines-tubeways-timberborn-update-7-adds-3d-terrain-unique-modular-transport-for-each-faction-more); [SteamDB patchnotes](https://steamdb.info/patchnotes/18346774)

**Map editor workflow and file format**
- Map Editor features (per community wiki): terrain raise/lower and soil painting, water sources for rivers/lakes/seasonal flows, starting positions, resource spawns (trees/bushes), map size configuration, multi-layer terrain (cliffs/valleys/plateaus), immediate playtest. Workflow: choose dimensions → raise ground and carve channels → place water sources → add vegetation → "Place at least one starting location marker" → set drought cycle and playtest; share via Steam Workshop or mod.io. — [timberborn.org: custom maps guide](https://timberborn.org/articles/modding-custom-maps-guide)
- `.timber` files are ZIP archives containing a JSON description (typically `world.json`); introduced in the Oct 2021 "better save system" patch ("new save files (as well as the map files) now use a .timber archive format"), much smaller than the earlier plain `.json`; old `.json` maps still load; editable by unzipping. — [fileinfo .TIMBER](https://fileinfo.com/extension/timber); [GOG forum patch notes 2021-10-20](https://gog.com/forum/timberborn/patch_notes_20211020_better_save_system_and_more); [gist: repack world.json](https://gist.github.com/maludwig/87ab60893330004bddddcec3d2f6a9d5)
- Official modding repo: a Unity project with tools to import Timberborn DLLs/assets, example mods, and a mod-builder; wiki covers "Blueprints" and JSON/DLL modding. No map-format spec in README. — [mechanistry/timberborn-modding](https://github.com/mechanistry/timberborn-modding)

**Water simulation and sources**
- Water Source: a 1×1×1 "Fluid Origin" that emits Water in Temperate weather and Badwater during Badtides; strength = flow in m³/s, most standard-map sources are strength 1; Diorama has two strength-3 sources; custom maps may use negative strength, making the source a sink; a source at the map edge blocks water above it from draining off-map (i.e., map edges otherwise drain). — [wiki.gg: Water Source](https://timberborn.wiki.gg/wiki/Water_Source)
- Badwater Source: emits badwater; behaviour during droughts has conflicting descriptions (stops unless a Badwater Discharge is built vs. flows until temperate weather returns); Iron Teeth Badwater Pressurizer keeps it flowing. — [wiki.gg: Badwater Source](https://timberborn.wiki.gg/wiki/Badwater_Source); [wiki.gg: Drought](https://timberborn.wiki.gg/wiki/Drought)
- Cell model (community guide): each tile holds a set amount of water, "1.0 unit of water per layer" when fully submerged; excess flows to lower tiles; pumps need ~0.3 depth; evaporation ≈0.045 units per exposed tile per day (10×10×3 reservoir = 300 units loses ≈4.5/day); water tanks 30/90 units, no evaporation; badwater is slightly heavier and sinks but mixes over time; during droughts river sources stop. — [timberborn.org: water physics guide](https://timberborn.org/articles/water-physics-fluids-guide)
- Player-reported flow cap: ~2.5 per block edge when water changes elevation (unverified Steam discussion); badwater drains at an effective flow height of 0.5 m over a 1 m drop (feature-request thread). — [Steam discussion](https://steamcommunity.com/app/1062090/discussions/0/599649197566820764); [featureupvote waterfall limit](https://timberborn.featureupvote.com/suggestions/569561/comment/667343)
- Badtide: both Water Sources and Badwater Sources emit badwater; contamination starts at 50% rising to 100% over 12 h, falls back over the last 12 h, drops to 0% when temperate returns; at 50% water neither irrigates nor contaminates; above 50% it contaminates terrain and kills plants (0.2–0.3 days). First-event durations (days): Easy drought 1/badtide 1; Normal 2–3/1; Hard 3–6/6–12; durations escalate per event with randomness. A cycle = one Temperate season + one Hazardous season (Drought or Badtide). — [wiki.gg: Badtide](https://timberborn.wiki.gg/wiki/Badtide)
- Update 5 added Badwater Sources to all maps; Update 1 added Underground Ruins ("Metal Deposits") to all maps; Update 6 added "more flexible start options". — [wiki.gg: Maps](https://timberborn.wiki.gg/wiki/Maps)
- A Dec 2024 wiki-flagged Reddit thread documents players hitting flooding/flow issues with 3D water. — [r/Timberborn flooding and flow issues](https://pol1.lr.ggtyler.dev/r/Timberborn/comments/1iy420o/flooding_and_flow_issues)

**Procedural / community generators**
- RTB TimberbornTerrainGenerator: "work in progress" random map generator, pure C# BepInEx + TimberAPI plugin; maps always square; min 32×32, max 384×384; the New-Map "Y" field is the seed (if Y == X, unseeded random); since 0.9.0 rewrite the only third-party code is FastNoiseLite; `settings.ini` presets "PlentifulPlains" (default), `HardyHills.ini` ("hard mode"), `MegaMesas.ini`, `stocksettings.ini`; changelog mentions "river sloping" fixes, "rivermap flooring logic", improved "water source block placement", badwater support (v1.8.1); generation "may appear frozen for a bit"; latest Thunderstore version 1.4.2 listed. README says to run the water sim after generation. — [R-T-B/TimberbornTerrainGenerator](https://github.com/R-T-B/TimberbornTerrainGenerator); [Thunderstore listing](https://timberborn.thunderstore.io/package/RTB/TimberbornTerrainGenerator/)
- mrCurry90 ExtraTerrainTools (v1.0; Update 6+; Steam Workshop/mod.io): Heightmap Generator (one-click procedural map), Mound Maker (conical geometry + multiple noise layers, with dig mode), Smoothing Brush, Path Painter (spline-driven terrain), Selection Editor (copy/paste/rotate/flip terrain + objects). Warns that changing large amounts of terrain while water exists "can cause problems with the game's water system" — save before Generate. — [mrCurry90/ExtraTerrainTools](https://github.com/mrCurry90/ExtraTerrainTools)
- Informati RandomMapGenerator also exists on Thunderstore (no details retrieved). — [Thunderstore: Informati/RandomMapGenerator](https://thunderstore.io/c/timberborn/p/Informati/RandomMapGenerator)
- A 2021 feature request "Procedural Map Generation - random map seeds" notes maps are fixed; no official response captured. — [featureupvote 215843](https://timberborn.featureupvote.com/suggestions/215843/comment/309461)

### Inferences
- Timberborn's terrain is effectively a column heightmap (0–16 in editor) plus, since Update 7, sparse 3D terrain blocks with a hard 3-block overhang limit; a 32³-chunk engine trivially represents this (a 256×256×22 map is 8×8×1 chunks).
- Water sources are point emitters with a scalar m³/s; negative strength as a sink and "edge = drain unless a source sits there" are cheap, expressive map-authoring primitives worth copying.
- Both community generators are noise-first (FastNoiseLite layered noise, conical mounds) and treat rivers as a post-pass ("rivermap flooring", "river sloping"); none use hydraulic erosion, and both note instability if water exists during regeneration — an engine should pause/reset the fluid sim while terrain is regenerated.

### Gaps
- No Mechanistry devblog on procedural/random map generation (2023–2025) was found; the "random map experiments" premise in the brief appears unsupported — I found only community mods.
- Exact fluid tick rate, per-edge flow formula, and the Update 6 3D solver design are not published; only player measurements (2.5/edge, 0.5 m effective head) exist.
- The `.timber` `world.json` schema (terrain array encoding, water source entity fields) was not retrievable from an official spec; only the ZIP+JSON container is confirmed.
- RTB's noise parameters and river algorithm live in `SettingsReadme.md`/source, not fetched.
- The exact in-editor water-source strength range and the official New-Map dialog limits (4–256) come from third-party guides only.

## Q2. Bounded-map generation in general (one-pass global algorithms, edge handling, guaranteed properties, validation/retry, seeded preview, RTS/city-builder references)

### Takeaway
For maps of ≤384² cells, O(n log n) global passes (Priority-Flood depression filling, flow accumulation, erosion) are affordable in one shot; shipped RTS/city-builders mostly guarantee gameplay properties by construction (tile edge-matching, per-player land + connection commands, spawn chosen after resource placement) rather than by validate-and-retry, with re-rolls left to the player.

### Cited Findings
- Priority-Flood (Barnes, Lehman, Mulla 2014): inserts DEM edge cells into a priority queue ordered by elevation and processes lowest-first; O(n) for integer and O(n log n) for float data; pseudocode ~20 lines, reference C++ <100 lines; "+Epsilon" variant guarantees every depression drains while preserving local flow directions; a flow-direction variant is "in essence, a depression-carving algorithm"; required because flow-routing needs every cell to have a direction and a path to the grid edge. Reference code: r-barnes/Barnes2013-Depressions; RichDEM for the full toolkit. — [arXiv 1511.04463](https://arxiv.org/pdf/1511.04463); [GitHub](https://github.com/r-barnes/Barnes2013-Depressions)
- Landscape-evolution models fill internally-draining regions before computing discharge and erosion/deposition. — [goSPL docs: inland depressions](https://gospl.readthedocs.io/en/stable/tech_guide/dep.html)
- The Riftbreaker: tiles are 128×128 m blocks (64×64 grid of 2×2 m cells) hand-built with painted material zones resolved at generation; prefabs (prop-filled scenes) fill masked gaps with random position/orientation, stitched copies ensure coverage; map assembly solves a simplified Wang-tile problem with 90° rotations, repetition allowed, edge-matching only; multi-tile structures (rock formations, lakes, rivers) placed whole then surrounded by random tiles; resource amounts fixed per mission, locations random with min/max density, yield peaks at deposit centre; player spawn chosen after resources as the spawn point closest to minimum basic resources; map sizes from a single tile to 12×12 tiles, Survival uses 5×5. No validate/retry step described. — [Game Developer: Systematic Chaos (Riftbreaker)](https://www.gamedeveloper.com/design/systematic-chaos-procedural-map-generation-in-the-riftbreaker)
- Age of Empires II DE RMS: `<LAND_GENERATION>` with `create_player_lands` arranges players in a circle with distance to centre controlled by land position values; connection types can link players to a non-player land (e.g., central island). — [Forgotten Empires: RMS Features](https://www.forgottenempires.net/age-of-empires-ii-definitive-edition/rms-features)
- Racket `aoe2-rms` DSL example: per-player land with terrain type, land percent, land position compiled to `create_land` blocks; included files are not transferred in the multiplayer lobby. — [aoe2-rms getting started](https://plt.cs.northwestern.edu/new-snapshots/doc/aoe2-rms@aoe2-rms-doc/getting-started.html)
- Community RMS note: island shapes kept circular by setting base terrain to water and player land size 0; game appears to process `create_player_lands` before other `create_land` (anecdotal). — [AoE forums](https://forums.ageofempires.com/t/some-random-map-scripts-ive-created/221035)
- Age of Empires III RMS (C-style): `rmSetMapSize(x,z)` in metres scaled by player count; `rmPlacePlayersCircular/Square/Line`; `rmCreateArea`/`rmSetAreaSize(minFraction,maxFraction)`; `rmSetAreaBaseHeight`, cliff type/height/edge; `rmCreateConnection` + `cConnectPlayers`; `rmCreateObjectDef` with min/max distance from player start and class-distance constraints. — [AoE support: Random Map Scripting Commands](https://support.ageofempires.com/hc/en-us/articles/8478836252564-Random-Map-Scripting-Commands)
- Civilization VI (community analysis of Firaxis Lua scripts): Continents family builds a low-granularity fractal for a few large landmasses then adds coastline ridges; sea level scales land size; Fractal does not equalise continent sizes so "a few re-rolls" may be needed; `FRAC_POLAR` region flag makes a fractal layer avoid map edges; a bug doubled continents by calling `TerrainBuilder.StampContinents()` twice; the river generator assumes no lakes. — [Got Lakes workshop discussion](https://steamcommunity.com/workshop/filedetails/discussion/916614621/3805027864673412199); [CivFanatics: Got Lakes](https://forums.civfanatics.com/resources/got-lakes-various-worlds-map-script.26512/)
- Against the Storm: a new map is generated each settlement; Eremite lists procedural generation among design pillars; Aron Pietroń and Michał Ogłoziński gave a 35-minute Roguelike Celebration talk (2023 preview listing) — content not retrieved. — [eremitegames devlog 1](https://eremitegames.com/devlog-1/); [Roguelike Celebration listing via setsideb](https://setsideb.com/tag/roguelikecelebration)
- Herbert Wolverson's 2020 Roguelike Celebration survey of procedural map generation covers integration of hand-crafted prefabs/vaults. — [amara transcript listing](https://amara.org/ro/videos/x1BBJJib1cR4/info/herbert-wolverson-procedural-map-generation-techniques/)
- Veloren stores "only a very coarse heightmap of the world on disk": a 1024×1024-chunk world's mapfile is ~16 MB (~16 bytes/chunk). — [Veloren devblog 32](https://veloren.net/blog/devblog-32)

### Inferences
- At Timberborn scale (≤256² columns), Priority-Flood+Epsilon is sub-millisecond-to-millisecond work and directly yields "every cell drains to an edge" — the exact guarantee Timberborn's edge-drain gameplay wants; it also produces a natural river network via flow accumulation on the filled surface.
- Guaranteeing a river from source to edge is easiest by construction: place sources at high-accumulation heads, carve the accumulation path downhill with Priority-Flood flow directions, then run the engine's own fluid sim as the validator (as RTB's README advises).
- Riftbreaker's "choose the spawn after resources" and AoE's "player land + connections" are the two standard patterns for start-area guarantees; both avoid retry loops. Civ VI shows the cost of not validating (re-rolls pushed to players).
- Seeded preview: all referenced systems derive maps from a seed; Timberborn mods repurpose an existing numeric field (Y) as the seed, suggesting the engine should make seed a first-class map-metadata field.

- No primary source on Against the Storm's generation algorithm (talk content not retrieved).
- No official AoE II RMS command reference was fetched (the support article is AoE III); AoE II details come from Forgotten Empires and community docs.
- No published generation-time numbers for any of these games.
- Anno and Frostpunk map generation: no sources gathered in this pass.

## Q3. Teardown: level construction, .vox format, scale, materials/destruction, lighting, what is procedural, community tools; general voxel asset import

### Takeaway
Teardown levels are XML scene files (`main.xml`) referencing MagicaVoxel `.vox` models (≤256³ per object, material by palette index), with groups/prefabs/instances/layers/tags in a built-in editor, Lua 5.1 gameplay scripts and Lua "voxscripts" for build-time procedural geometry; voxels are ~10 cm, each shape is its own dense grid that moves rigidly, destruction splits shapes by connectivity, and lighting is GPU ray-traced against a 1-bit-per-voxel occupancy bitmap of the whole level. The `.vox` format is a RIFF-style chunk file (SIZE/XYZI/RGBA + nTRN/nGRP/nSHP scene graph, MATL materials, 1-byte packed rotations).

### Cited Findings

**Level/mod structure and editor**
- Mod = one folder in Documents/Teardown/mods; required `info.txt` (name, author, description, optional tags: Map, Gameplay, Asset, Vehicle, Tool); root files `main.lua`, `main.xml`, `options.lua`, `preview.jpg` (≤1 MB); `id.txt` auto-created on first publish; names restricted to Latin alphanumerics. A mod with `main.xml` is a "Content" mod; other levels loaded by `StartLevel("level2","MOD/mymodlevel2.xml")` with optional layer string ("heist secrets"); `MOD` and `LEVEL` path keywords. — [teardowngame.com/modding](https://teardowngame.com/modding/)
- Editor: F5 play / F4 back; Scene Explorer mirrors XML order; Groups pass properties down by inheritance; right-click a group → Prefab saved as its own XML, Instances reference it, committing updates all instances; Property Window colours explicit (white), default (grey), inherited (blue); Tags with values queried by `FindShapes()`/`GetTagValue()`; Layers via group `layer` property with "minus layers"; search (CTRL-F). `spawn.txt` maps prefab paths to spawn-menu categories ("path/to/mycar.xml : Cars/My car"); static objects become dynamic when spawned. Water node positions can't change at runtime. — [teardowngame.com/modding](https://teardowngame.com/modding/)
- Lua API: Teardown uses Lua 5.1; scripts can take parameters defined in the level XML. — [Teardown scripting API 2.1.0](https://teardowngame.com/modding/api.html)
- Changelog (undated): 0.6 Steam Workshop + custom tools; 0.7.0 editor search/apply-properties/layers; 0.8.0 right-click opens vox/Lua from the editor; 1.3.0 specular materials for MagicaVoxel 0.99.7; 1.4.0 Creative Mode, mod profiler, CreateShape/ExtrudeShape; 1.7.0 mirrorx/y/z on vox/voxbox/voxagon, "Place from above", "Convert to voxagon"; 2.0.1 fix for heightmap-generated vox objects; 2.0.3 lava-style water volumes; latest listed 2.2.0 (multiplayer prefab Spawn() path check). — [teardowngame.com/changelog](https://teardowngame.com/changelog)
- SteamDB: version 0.4.6 added the level editor; later patches added fog/sky colour editing and a Material Panel with 66 materials for ground/background walls; v1.2 (Oct 2022) press release described Teardown as long having "a built-in level editor and Steam Workshop integration". — [SteamDB 10113466](https://steamdb.info/patchnotes/10113466); [phenixxgaming on 1.2](https://phenixxgaming.com/2022/10/25/teardown-gets-new-update-with-featured-mods-list)

**Voxel scale, shapes, destruction, lighting (Dennis Gustafsson, SED podcast Dec 2024)**
- One voxel ≈10 cm, "inspired by MagicaVoxel"; each object has its own voxel grid that rotates/moves freely in world space; integer-aligned voxels avoid polygon-destruction degeneracies; removing voxels breaks objects into pieces that become rigid bodies; connected-part detection added months after EA (before it, one remaining voxel could hold up a house); searches must handle levels of "hundreds of millions of voxels"; no structural-integrity/load-path simulation (joints fake it). Lighting moved from screen space to voxel space: GPU ray tracing against a bit-per-voxel bitmap of the whole level marking light blockers, updated by CPU in background (large movers like a yacht are expensive); original OpenGL texture limit capped the world at 4,000 voxels across; exploring Vulkan hardware RT/path tracing to remove the world-size limit and the bitmap; engine is custom (OpenGL originally, D3D12 for consoles by Saber). — [SED1772 transcript](https://softwareengineeringdaily.com/wp-content/uploads/2024/12/SED1772-Teardown.txt)
- Press summaries: Teardown has no GI; ray tracing is used for ambient occlusion, soft shadows and specular occlusion; each shape stored as an uncompressed dense 3D grid; the next-gen engine splits shapes into 8×8×8 chunks tracked by a 3D bitmap; multiplayer sync relies on determinism rather than sending voxel data. — [80.lv: new voxel engine](https://80.lv/articles/teardown-creator-is-working-on-a-new-voxel-engine); [80.lv: multiplayer and destruction tech](https://80.lv/articles/teardown-developer-breaks-down-multiplayer-and-voxel-destruction-tech); [blog.voxagon.se](https://blog.voxagon.se/2024/12/29/year-summary.html)

**Materials and asset rules (official)**
- Material is set only by palette index (e.g., index 9 = grass), never by colour; max object 256×256×256 voxels, ~128³ "generally fine", flat 256×256×10 acceptable; split hollow objects (tree trunk/crown, walls/floors) for performance; later objects overwrite earlier ones where overlapping; voxels must connect by faces (edge/corner contact doesn't hold); avoid soft inside hard; hardness classes: soft (glass, grass, dirt, plastic, wood, plaster), medium (concrete, brick, weak metal), hard (hard masonry, hard metal), unbreakable (heavy metal, rock); render props set in MagicaVoxel (Metal for most, Glass, Emissive ≥ power 2, emissives don't light the scene). — [teardowngame.com/modding](https://teardowngame.com/modding/)

**Procedural content in Teardown (voxscript)**
- Voxscript (Lua) generates voxel geometry in the editor at build time: parameters `GetFloat/GetInt/GetBool/GetString/GetColor`, seeded `Randomize`, `GetRandomFloat/Int`; `CreateMaterial(type, r,g,b, …)`; `CreateBrush` loads a `.vox` (optionally a named object) with `FlipBrush/RotateBrush/TranslateBrush/GetBrushSize`; `Material(0)` clears; `Vox(x,y,z[,rot])` creates a shape; `Box/Sphere/Line/Set/Get`; `LoadImage` + `Heightmap` builds terrain from a PNG (red = height, green = grass). API version 1.6.3. — [Teardown voxscript API](https://teardowngame.com/modding/voxscript.html)
- A community Google Doc covers terrain/heightmap workflows for Teardown map makers (not fetched). — [Terrain guide (Google Doc)](https://docs.google.com/document/d/1QClYTQXLVRIDuUNYZu3WtsPIPJ43gK5tevP4lGm1mzY/export?format=pdf)
- Community asset guide: make models in MagicaVoxel, open the built-in editor, import `.vox`; place `.vox` next to the level XML in Documents/Teardown/mods. — [get-teardown.readthedocs](https://get-teardown.readthedocs.io/en/latest/mods/creating-your-own-assets.html); [Steam discussion](https://steamcommunity.com/app/1167630/discussions/0/4811511685067107374)

**MagicaVoxel .vox format**
- Header `'VOX '` + int32 version 150; RIFF-style chunks: 4-byte id, int32 content bytes N, int32 child bytes M; `MAIN` root; optional `PACK` (numModels); `SIZE` (int32 x,y,z; z is gravity/up); `XYZI` (int32 numVoxels then 4 bytes per voxel x,y,z,colorIndex — 1 byte each, so 0–255 per axis); `RGBA` 256×4 bytes with file index i → palette i+1; default palette table when RGBA absent; `MATT` deprecated. — [ephtracy vox spec](https://github.com/ephtracy/voxel-model/blob/master/MagicaVoxel-file-format-vox.txt)
- Extension: multiple SIZE/XYZI pairs = multiple models (id = order); scene graph alternates nTRN → nGRP → nTRN → nSHP; `nTRN` has node id, DICT attrs (`_name`, `_hidden`), child id, reserved −1, layer id, frame count, per-frame DICT with `_r` (packed int8 rotation), `_t` (int32×3 translation), `_f`; `nGRP` child list; `nSHP` model ids per frame; ROTATION packs a row-major 3×3 signed permutation into one byte (bits 0–1 column of row 1, bits 2–3 column of row 2, bits 4/5/6 signs of rows 1/2/3); `MATL` DICT: `_type` (_diffuse/_metal/_glass/_emit), `_weight`, `_rough`, `_spec`, `_ior`, `_att`, `_flux`, `_plastic`; `LAYR`, `rOBJ`, `rCAM`, `NOTE` (palette colour names), `IMAP` (256 int32 index map). STRING = int32 length + bytes; DICT = int32 count + key/value STRING pairs. — [ephtracy vox extension spec](https://github.com/ephtracy/voxel-model/blob/master/MagicaVoxel-file-format-vox-extension.txt)
- ogt_vox.h (opengametools): single-header MagicaVoxel scene reader/writer/merger; `ogt_vox_read_scene` from a buffer (buffer freeable afterwards); scene = instances, models, layers, palette; each instance has a column-major 4×4 transform; companion `ogt_voxel_meshify.h` converts voxel grids to meshes. — [jpaver/opengametools README](https://github.com/jpaver/opengametools/blob/master/README.md)
- dot_vox (Rust) walks the scene graph composing rotations down the tree (`traverse_graph` example); odin-vox and threejs-vox-loader are other loaders. — [dot_vox traverse_graph](https://docs.rs/crate/dot_vox/latest/source/examples/traverse_graph.rs); [odin-vox](https://github.com/jakubtomsu/odin-vox)

### Inferences
- Teardown's per-shape dense grid + rigid transform model is the opposite of a world-aligned chunk grid; an engine with 32³ chunks would import `.vox` by blitting (resampling) each nSHP instance through its composed nTRN transform into world voxels, which is exact for `.vox` rotations (signed axis permutations) and translations (integers) — no interpolation needed.
- Because `.vox` coordinates are 1 byte, any model >256 per axis must be split into multiple models in one file (MagicaVoxel's world editor does this); the importer must handle PACK/multi-model files and the scene graph, not just the first SIZE/XYZI.
- Palette-index-as-material is the simplest mapping onto a block registry: an import table from palette index (or `NOTE` colour names / `MATL` type) → block id.
- Teardown's "procedural" surface is small and build-time only (voxscript, heightmap from PNG, random prop spawning via Lua `Spawn()`); the engine equivalent is a build-time Lua/script hook that writes voxels into chunks.

### Gaps
- The Teardown XML schema (attributes of `scene`, `vox`, `voxbox`, `body`, `shape`, `instance`, `light`, `water`, `scale`, `density`, `strength`) was not retrievable: the fandom wiki returned HTTP 402 and the official page defers to in-editor help.
- No official statement of the 10 cm scale beyond the podcast; no published per-level voxel/shape limits for the current (2.x) engine except the historic 4,000-voxel OpenGL cap.
- The exact Teardown 1.0 release date and the editor's first-release date (0.4.6) are undated in the official changelog.
- Game "Creative mode" (1.4.0) tool details not retrieved.

## Q4. Authored-plus-procedural composition (prefab scattering, room templates, kit-bashing, Minecraft structure templates, Luanti schematics, Spelunky stitching, destruction granularity)

### Takeaway
Every shipped reference uses the same three primitives: (1) a template format with a palette, per-voxel entries and placement metadata (rotation in 90° steps, mirror, per-node probability/force-place, integrity/decay), (2) a grid of slots filled from template pools with edge/adjacency rules, and (3) a post-pass that scatters props/resources under distance constraints. Destruction granularity is a design split: Teardown breaks per-object grids by connectivity; block games destroy per voxel in a shared grid.

### Cited Findings
- Minecraft structure template (`.nbt`, gzip NBT, data pack `data/<ns>/structure`, saved from structure blocks to `generated/<ns>/structure`): root `DataVersion`, `size` (3 ints), `palette` (list of {Name, Properties}), optional `palettes` (alternative palettes chosen per position by coordinates; used by shipwrecks), `blocks` (list of {state: palette index, pos: 3 ints, nbt: optional block-entity data}), `entities` ({pos doubles, blockPos ints, nbt}); positions relative to the −X,−Y,−Z corner; palette format since 1.10, DataVersion since 1.11; Bedrock `.mcstructure` v2 adds zlib `compression`. — [Minecraft Wiki: Structure file](https://minecraft.wiki/w/Structure_file)
- Structure Block limits: Java max 48×48×48; Bedrock 64×384×64 (older wiki copies say 64×256×64); rotation 0/90/180/270° clockwise; mirror none / left-right (X at 0°) / front-back (Z); integrity 0.0–1.0 with seed removes blocks randomly to mimic decay; Paper API confirms 48³. — [Minecraft Wiki mirror: Structure Block](https://wiki.ronlab.site/content/minecraftwiki_en_all_maxi_2025-11/Structure_Block); [Paper API Structure](https://jd.papermc.io/paper/1.21.5/org/bukkit/block/Structure.html)
- Sponge Schematic (`.schem`, current version 3, 2021-05-04): gzip NBT with Width/Height/Length, `BlockPalette` (renamed from Palette in v3), `BlockData` varint array of W×H×L palette indices indexed `x + z*Width + y*Width*Length`, entity and biome support since v2 (2019-05-08), 3D biomes in v3, `RequiredMods` list; parsers reject varints >5 bytes. — [SpongePowered Schematic-Specification v3](https://github.imc.re/SpongePowered/Schematic-Specification/blob/master/versions/schematic-3.md); [spec repo](https://github.com/SpongePowered/Schematic-Specification)
- Luanti `.mts` schematic / Lua table: `size` vec3; `yslice_prob` list of {ypos, prob} (prob default 255); `data` flat [z[y[x]]] list of {name, prob 0–255 (0/1 never, 254/255 always, else p/256), param2, force_place}; flags `place_center_x/y/z`, `force_placement` (non-"ignore" nodes replace existing). — [Luanti API: schematics](https://api.luanti.org/schematics/)
- Spelunky (Kazemi): level = 4×4 grid of 16 rooms, each 10×8 = 80 tiles stored as 80-char strings; four room types each with ~8–16 templates (≈50 layouts per tileset); template chosen by the room's role on the entrance→exit solution path; templates mix fixed and probabilistic tiles plus obstacle blocks; separate generator scripts per area (cave, jungle, yeti, temple); Kazemi argues obstacle generation matters more than room choice for replayability. — [Spelunky Generator Lessons](https://tinysubversions.com/spelunkyGen2/); [Part 2 Room Generation](https://tinysubversions.com/2013/10/spelunky-generator-lessons-part-2-room-generation/index.html); [2010 modding tutorial](https://www.tinysubversions.com/2010/01/tutorial-modding-spelunkys-level-generator/index.html); [Procedural Space 2009](https://www.tinysubversions.com/2009/09/spelunkys-procedural-space/index.html)
- Riftbreaker: hand-built 64×64-cell tiles with randomised material zones; prefabs fill masked gaps with props at random position/orientation; Wang-tile edge matching with 90° rotations; multi-tile set pieces placed whole. — [Game Developer: Riftbreaker](https://www.gamedeveloper.com/design/systematic-chaos-procedural-map-generation-in-the-riftbreaker)
- Teardown prefabs: group → prefab XML, instances reference it, commit propagates; `spawn.txt` registers prefabs as spawnables; 1.7.0 added mirrorx/y/z on vox/voxbox; voxscript `CreateBrush`/`RotateBrush`/`FlipBrush` stamp `.vox` brushes into generated shapes. — [teardowngame.com/modding](https://teardowngame.com/modding/); [changelog](https://teardowngame.com/changelog); [voxscript](https://teardowngame.com/modding/voxscript.html)
- Teardown destruction: per-object dense grids; removing voxels then connectivity search splits objects into rigid debris; no load-path simulation; joints fake structure. — [SED1772 transcript](https://softwareengineeringdaily.com/wp-content/uploads/2024/12/SED1772-Teardown.txt)
- Minecraft Anvil stores blocks in a single world grid with per-section palettes (see Q5), i.e., per-voxel destruction with no object identity. — [Minecraft Wiki: Chunk format](https://minecraft.wiki/w/Chunk_format)

### Inferences
- A unified "template" record for the engine would be: size, palette of block ids, dense or sparse voxel entries with per-entry probability and force flag (Luanti), optional alternative palettes (Minecraft), integrity/decay (Structure Block), 24 signed-permutation rotations (.vox packing) or at least 4 yaw rotations + 3 mirrors (Structure Block/Teardown).
- Blitting into 32³ chunks: a template of ≤48³ or ≤256³ can straddle up to 2³–9³ chunks; the importer should iterate template voxels in chunk-major order (or clip the template AABB per chunk) so each chunk is dirtied once, and fluid-sim wake-ups (the engine's "waking from edits") happen per touched chunk.
- Per-voxel vs per-object destruction: a Timberborn-like game needs only per-voxel terrain edits plus the fluid wake; a Teardown-like game needs an additional "object" layer (shape id per voxel or separate movable grids) and a connectivity/flood-fill pass on edit. Keeping a per-voxel "structure id" in chunk data is the cheapest bridge.

### Gaps
- No primary Minecraft Wiki text on jigsaw blocks/pools was fetched (page truncated); only the template NBT and structure-block limits are covered.
- Luanti `place_schematic` rotation options (0/90/180/270/random) and `.mts` byte layout were not retrieved (the API page section lacked them).

## Q5. Save formats for voxel worlds (Minecraft Anvil, Luanti SQLite, Veloren, palette/RLE per chunk, versioning)

### Takeaway
Shipped formats converge on: fixed-size chunk/section payloads addressed by an index table or keyed DB row, per-section palette + bit-packed indices (Minecraft) or raw node arrays with a name→id mapping (Luanti), whole-payload compression (zlib → zstd/LZ4), and an explicit version number per chunk with forward data-fixers. Veloren shows the alternative: persist only diffs/coarse data and regenerate the rest.

### Cited Findings
- Minecraft region files (`r.x.z.mca`, 32×32 chunks, region = chunk >> 5): 4 KiB sectors; sector 0 = location table, sector 1 = timestamp table, each 1024 big-endian int32 entries indexed `x + 32z`; location = 3-byte sector offset + 1-byte length in sectors (max 255 sectors ≈ 1020 KiB); chunk payload = int32 length + 1-byte compression type + data; last chunk padded to 4096; compression ids 1 GZip (unused), 2 Zlib (what the client writes), 3 uncompressed, 4 LZ4 (since 24w04a, server.properties), 127 custom (24w05a, namespaced string); oversized chunks get compression id +128, length 1, and data in `c.x.z.mcc`. — [Minecraft Wiki: Region file format](https://minecraft.wiki/w/Region_file_format); [wiki.vg Map Format](https://wiki.vg/Map_Format)
- Anvil (1.2 / 12w07a) changed only the chunk NBT, keeping the region container; block order changed from XZY to YZX for better compression. — [Anvil format (wiki mirror)](https://wiki.ronlab.site/content/minecraftwiki_en_all_maxi_2025-11/Anvil_format)
- Chunk NBT: sections of 16×16×16 indexed `y*256 + z*16 + x`; `block_states.palette` (vanilla writes ≤4096 entries) + `data` long array of 4096 packed indices, bits per index = max(4, ceil(log2(palette size))), indices never span a 64-bit long (padding bits wasted), single-entry palette omits `data`; `biomes` palette over 4×4×4 cells (≤64 per section, no 4-bit minimum); heightmaps 256 values × 9 bits (0–384), 7 per long = 37 longs (36 before 1.16); `Status` pipeline empty → structure_starts → structure_references → biomes → terrain → features → initialize_light → light → spawn → full; `DataVersion` int per chunk; 21w43a removed the `Level` wrapper and added `yPos`, `below_zero_retrogen`, `blending_data`; upcoming 26.4-snap1 stores biomes per block and renames `Status`→`status`. — [Minecraft Wiki: Chunk format](https://minecraft.wiki/w/Chunk_format)
- Luanti: world is 16×16×16-node MapBlocks; `map.sqlite` single `blocks` table, keyed by `(x,z,y)` since 5.12.0, previously an integer `pos` packing three 12-bit fields (offset 0x800, Z highest); default backend SQLite3, set in `world.mt` (`backend`, `gameid`, `auth_backend`, `blocksize`, `load_mod_*`); `map_meta.txt` holds `seed` etc. MapBlock blob (big-endian): version byte, flags byte (underground, day/night diff, lighting expired, generated), 16-bit lighting-complete (v27+); timestamp and name→id mapping first in v29; `content_width` 2 bytes (v24+), `params_width` 2; arrays of 4096 `param0/param1/param2` indexed `z*256 + y*16 + x`; node metadata (v2 from v28), node timers (10 bytes each, v25+), static objects; zlib before v29, zstd for the whole block after the version byte from v29. — [luanti world_format.md](https://raw.githubusercontent.com/luanti-org/luanti/master/doc/world_format.md); [Luanti docs: database backends](https://docs.luanti.org/for-server-hosts/database-backends/)
- Veloren: terrain persistence writes build-mode edits under a `terrain` directory (or `VELOREN_TERRAIN`), with versioned raw chunk formats (Version 1–3); chunks are 32×32×16 (older blog); the world keeps only a coarse heightmap on disk (~16 MB for 1024×1024 chunks). — [docs.veloren.net terrain_persistence](https://docs.veloren.net/src/veloren_server/terrain_persistence.rs.html); [version module](https://docs.veloren.net/veloren_server/terrain_persistence/version/index.html); [devblog 32](https://veloren.net/blog/devblog-32)
- Timberborn: `.timber` = ZIP containing JSON (`world.json`), replaced plain `.json` saves in Oct 2021 for size; older `.json` still loads (an implicit versioning/migration path). — [fileinfo](https://fileinfo.com/extension/timber); [GOG patch notes](https://gog.com/forum/timberborn/patch_notes_20211020_better_save_system_and_more)
- Sponge `.schem` v3 uses a per-file palette + varint indices and a `RequiredMods` list to make block ids portable across mod sets. — [Schematic-Specification](https://github.com/SpongePowered/Schematic-Specification)

### Inferences
- For a 32³ chunk the Minecraft recipe translates to: palette of block ids (registry names, not numeric ids, so saves survive registry changes), 32768 bit-packed indices (min 4 bits → 16 KiB; 1 entry → 0 bytes), then zstd/LZ4 over the payload; a per-chunk `data_version` plus region-level index table (or SQLite keyed by chunk coords for simplicity, as Luanti).
- Timberborn-scale maps (8×8×1 chunks) are small enough that a single-file ZIP+JSON/CBOR container with embedded metadata (seed, size, cycle settings, sources, start markers) is viable and editor-friendly; Anvil-style regions only pay off for open worlds.
- Fluid state must be saved alongside blocks for "edits persist": per-column/per-cell water volume and contamination (Timberborn-style) or the engine's own cell state; Veloren-style "generate + diff" is a valid fallback for procedural maps if generation is deterministic from seed + version.
- Explicit `DataVersion` with ordered fixers (Minecraft) and "old format still loads" (Timberborn, Luanti serialization versions 22–29) are the two proven migration strategies; both require the version number to be written from day one.

### Gaps
- Veloren's current on-disk chunk layout (what each version encodes) was not retrieved beyond module names.
- No quantitative compression ratios for Anvil/Luanti chunks were found in primary sources (third-party tool claims about "zlib level 1" were discarded as marketing).

## Q6. Editor requirements: brushes, prefab placement, undo, map metadata

### Takeaway
The two reference editors (Timberborn Map Editor, Teardown editor) define a minimal feature set: terrain brushes with relative/absolute height and clamped limits, overhang/layer tools, point-emitter placement with scalar strength, start markers and resource/ruin placement, map-level settings (size, seed, cycle/difficulty), instant playtest, and (Teardown) a scene tree with groups, inheritance, prefabs/instances, tags, layers and search; community mods add smoothing, spline paths, copy/paste/rotate/flip selections and one-click generation.

### Cited Findings
- Timberborn editor: terrain raise/lower and soil painting, water sources, starting positions, resource spawns, map size configuration, multi-layer terrain, immediate playtesting; map settings include drought cycle; must place ≥1 starting location marker; publish to Steam Workshop or mod.io. — [timberborn.org custom maps guide](https://timberborn.org/articles/modding-custom-maps-guide)
- Timberborn editor (wiki.gg): toolbar with landscaping and object-placement tool groups; map objects = trees, bushes, fluid and metal sources; Map Editor Options duplicated top-left; season/fluid-simulation/visibility toggles top-right; terrain max 16; Fluid editing tools, Objects and Ruins tools are separate tool pages. — [wiki.gg: Map Editor](https://timberborn.wiki.gg/wiki/Map_Editor)
- Update 7 editor: overhang sculpting tool (≤3 blocks sideways), layer tool, relative terrain brush greys out out-of-limit tiles; later patches show sculpt-area measurements. — [SteamDB 18346774](https://steamdb.info/patchnotes/18346774)
- Water source strength is a per-map editor value in m³/s; negative = sink. — [wiki.gg: Water Source](https://timberborn.wiki.gg/wiki/Water_Source)
- ExtraTerrainTools adds: one-click Heightmap Generator, Mound Maker (cone + multi-noise, dig mode), Smoothing Brush, Path Painter (splines), Selection Editor (copy/paste/rotate/flip terrain and objects; flip buggy for some objects); warns large terrain edits with live water break the sim. — [mrCurry90/ExtraTerrainTools](https://github.com/mrCurry90/ExtraTerrainTools)
- RTB generator reuses the New-Map Y field as seed and exposes `settings.ini` profiles with export/import GUI (v1.6.1/1.6.3). — [R-T-B/TimberbornTerrainGenerator](https://github.com/R-T-B/TimberbornTerrainGenerator)
- Teardown editor: Scene Explorer in XML order, right-click add, group property inheritance, prefab convert/commit, Property Window explicit/default/inherited colouring, auto-updated transform properties, tags with values, layers and minus-layers, help/tooltips, search; F5/F4 play loop; later versions add free-cam, mirror properties, "Place from above", shape counter, 4K-friendly ImGui, mod profiler. — [teardowngame.com/modding](https://teardowngame.com/modding/); [changelog](https://teardowngame.com/changelog)
- Minecraft Structure Block offers save/load with rotation, mirror, integrity+seed, and `/place template`. — [Structure Block (wiki mirror)](https://wiki.ronlab.site/content/minecraftwiki_en_all_maxi_2025-11/Structure_Block)
- Map metadata examples: Timberborn `.timber` JSON (size, cycle settings per the editor options), Luanti `map_meta.txt` (`seed`) and `world.mt` (gameid, backend), Minecraft `DataVersion`. — [fileinfo .timber](https://fileinfo.com/extension/timber); [luanti world_format.md](https://raw.githubusercontent.com/luanti-org/luanti/master/doc/world_format.md); [Chunk format](https://minecraft.wiki/w/Chunk_format)

### Inferences
- Undo: none of the sources document their undo model; given chunk-granular storage, a chunk-diff (before/after palette+indices per touched chunk) undo stack is the natural fit and doubles as the persistence delta.
- Fluid interaction is the editor's hardest requirement, as both Timberborn community tools warn: the editor needs an explicit "fluid paused / reset / resimulate" control (Timberborn exposes a fluid-simulation toggle top-right) and should re-run the sim as validation after bulk edits or generation.
- Prefab placement in a chunked world needs: rotation (4 yaw + mirrors minimum; 24 if importing `.vox` transforms), ghost preview, overwrite vs. force-place policy, and tags/metadata (Teardown) so scripts can find placed instances.

### Gaps
- No source describes undo/redo implementation in either editor.
- Timberborn map-metadata fields (thumbnail, description, author) in `world.json` were not confirmed from an official schema.

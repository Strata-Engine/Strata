# Noise primitives and noise libraries for voxel terrain generation

Scope: a comparison of noise algorithms, fractal combinators, hashing, determinism, and the libraries that implement them, aimed at an engine (March, C FFI) that today has only hand-written 2D value noise (lattice hash, smoothstep, 3-octave fBm, ridged variant). Research date: 2026-11-11. All performance figures below are the libraries' own published numbers unless stated; ns/sample values are derived by me from the published Mpts/s figures (1e3 / Mpts/s) and are marked as derived.

## Value vs Perlin vs Simplex vs OpenSimplex2 (S and F): quality, artefacts, cost, patents, heightmap vs 3D density

### Takeaway
Cube-lattice noises (Value, Value-Cubic, Perlin) are the cheapest but are visibly square-biased; simplex-family noises (Simplex, OpenSimplex2F/2S) remove most of that bias at roughly 1.3-1.5x the per-sample cost. The Simplex patent expired 8 Jan 2022 and OpenSimplex2 is CC0 and claims no patent coverage, so there is no longer a legal reason to avoid either. For a voxel engine the practical recommendation from the sources is OpenSimplex2 (F) with domain rotation ("ImproveXZ") for 3D density sampled in a Y-up world, and OpenSimplex2S where ridged/smooth output matters; Red Blob argues that for heightmaps the choice of base noise matters far less than how octaves are combined and redistributed.

### Cited Findings
- Perlin noise is "visibly square-biased": features fall mostly at 45 or 90 degrees to the input axes, because gradients sit only at cube-grid vertices. Value and Value-Cubic noise share the same grid problem — [noiseposti.ng, "The Perlin Problem: Moving Past Square Noise" (KdotJPG, 2022)](https://noiseposti.ng/posts/2022-01-16-The-Perlin-Problem-Moving-Past-Square-Noise.html)
- Ken Perlin's own course notes say the original implementation "contains visible directional artifacts which are an unavoidable consequence of its underlying algorithm", and that on a rotated domain a casual viewer can pick out the grid orientation; also that random gradient assignment lets adjoining lattice points get very similar gradients, producing visible correlation — [Perlin, "Noise Hardware" (SIGGRAPH 2001 course ch. 9)](https://userpages.cs.umbc.edu/olano/s2001c24/ch09.html)
- Simplex-type noise (Simplex, OpenSimplex, OpenSimplex2, OpenSimplex2S) uses a grid of simplices, which reduces axis alignment; gradient-set quality also matters ("Good sets promote visual isotropy") — [noiseposti.ng](https://noiseposti.ng/posts/2022-01-16-The-Perlin-Problem-Moving-Past-Square-Noise.html)
- Domain rotation: a linear rotation of the input that sends one coordinate (typically Y or Z) up the cube-grid main diagonal, unit vector <g,g,g>, g ≈ 0.577350269189626, with the other two axes assigned via a skew constant (the `noise3_ImproveXZ` transform). Requires at least 3D noise. It works on Perlin/Value/Value-Cubic and (with smaller effect) on simplex noise, helps most when 3D noise is used for 2D-ish work "such as overhanging voxel terrain", and comes "with virtually no performance penalty" — [noiseposti.ng](https://noiseposti.ng/posts/2022-01-16-The-Perlin-Problem-Moving-Past-Square-Noise.html)
- Red Blob Games: "it matters little which noise you use (Simplex, OpenSimplex, Perlin, value noise, midpoint displacement, diamond-square...)" for this type of heightmap generator; Perlin can show axis-aligned artefacts and switching to Simplex or rotating some octaves is a fix — [Red Blob Games, Making maps with noise functions](https://www.redblobgames.com/maps/terrain-from-noise/)
- OpenSimplex2F: "closest in appearance to Simplex and about as fast as common Simplex implementations"; 3D uses a rotated body-centred-cubic grid. OpenSimplex2S: closest to 2014 OpenSimplex, larger vertex contribution ranges, better uniformity in 3D/4D, "a smoother copy of OpenSimplex2(F)", and the author recommends it for ridged noise. 2S and 2014 OpenSimplex are "not as fast" because they add more vertex contributions — [KdotJPG/OpenSimplex2 README](https://github.com/KdotJPG/OpenSimplex2); [noiseposti.ng](https://noiseposti.ng/posts/2022-01-16-The-Perlin-Problem-Moving-Past-Square-Noise.html)
- OpenSimplex2 3D "ImproveXY" orientation keeps similar properties along the third axis so XY slices look good; the classic-lattice fallback is "less ideal when X/Y planes are the main focus". FastNoiseLite exposes both ImproveXYPlanes and ImproveXZPlanes as its 3D rotation types (XZ being the one for a Y-up voxel world) — [KdotJPG/OpenSimplex2](https://github.com/KdotJPG/OpenSimplex2); [FastNoiseLite wiki](https://github.com/Auburn/FastNoiseLite/wiki/Documentation)
- Patent: US 6,867,776 covered simplex noise in 3D and higher for textured image synthesis only when implemented with the specific claimed techniques; it expired 8 January 2022 — [Wikipedia, Simplex noise](https://en.wikipedia.org/wiki/Simplex_noise). OpenSimplex2's author: "To the best of my non-lawyer knowledge, no patent claims cover anything implemented here" — [KdotJPG/OpenSimplex2](https://github.com/KdotJPG/OpenSimplex2)
- Per-sample cost, FastNoiseLite C++ (Intel 7820X @ 4.9 GHz, clang-cl /O2), Mpts/s: 2D Value 114.01, Perlin 92.83, Simplex(OpenSimplex2) 71.30, Cellular 39.15; 3D Value 64.13, Perlin 47.93, Simplex 36.83, Cellular 12.49 — [FastNoiseLite README](https://github.com/Auburn/FastNoiseLite). Derived ns/sample: 2D Value ≈ 8.8, Perlin ≈ 10.8, Simplex ≈ 14.0, Cellular ≈ 25.5; 3D Value ≈ 15.6, Perlin ≈ 20.9, Simplex ≈ 27.2, Cellular ≈ 80.
- Per-sample cost, FastNoise2 AVX2 (same CPU), Mpts/s: 2D Value 776.33, Perlin 624.27, Simplex 466.03, Cellular 194.30; 3D Value 494.49, Perlin 261.10, (Open)Simplex 268.44, Cellular 52.43 — [FastNoise2 README](https://github.com/Auburn/FastNoise2). Derived ns/sample 3D: Value ≈ 2.0, Perlin ≈ 3.8, Simplex ≈ 3.7, Cellular ≈ 19.
- stb_perlin's author notes Perlin's gradient function has 12 cases so some occur more often than others, and he adjusted the weights to reduce this bias — [stb_perlin.h](https://github.com/nothings/stb/blob/master/stb_perlin.h)
- A 2025 blog proposes "Quadratic noise", a Perlin variant with ~20% extra cost that reduces grid artefacts, and notes Simplex's downsides are "speed and implementation complexity" — [milesoetzel.substack.com](https://milesoetzel.substack.com/p/introducing-quadratic-noise-a-better) (single-author blog; treat as one opinion)
- Minecraft (Zucconi's write-up) uses 3D fractal "Perlin" noise interpreted as density ("anything lower than 0 would be air"), and warns against a "Perlin-first mindset", suggesting Simplex/OpenSimplex as alternatives — [Alan Zucconi, The World Generation of Minecraft](https://www.alanzucconi.com/2022/06/05/minecraft-world-generation/)

### Inferences
- Cost ladder in 3D scalar code is roughly Value 1.0x : Perlin 1.35x : OpenSimplex2 1.75x : Cellular 5x (from the FastNoiseLite table). Upgrading the engine's value noise to OpenSimplex2 roughly doubles the per-octave cost in 3D but removes the square bias that fBm of value noise cannot hide.
- For 2D heightmaps, keeping value noise is defensible if octaves are decorrelated (offsets/rotation per octave, see fractal section); for 3D density, square bias shows up directly as 45/90-degree cliffs and overhangs, so OpenSimplex2 + ImproveXZ rotation (or at minimum domain-rotated Perlin/value) is the better fit.
- Value noise smoothed with smoothstep (C1) will show visible creases in derivatives; Value-Cubic or gradient noise gives smoother surfaces. (General inference; no specific source captured.)

### Gaps
- No source gave a direct, same-harness benchmark of OpenSimplex2F vs OpenSimplex2S; the FastNoiseLite table's "Simplex" column is OpenSimplex2 (asterisked, unexplained) and has no 2S column.
- I could not retrieve KdotJPG's Reddit posts comparing artefacts with images; the noiseposti.ng article covers the same ground.

## Fractal combinators: fBm, ridged, billow, hybrid multifractal, ping-pong, domain warping; typical parameters

### Takeaway
Industry defaults are lacunarity 2.0, gain 0.5 (equivalently Hurst H = 1, G = 2^-H), and 3-6 octaves; FastNoiseLite defaults to 3 octaves, stb_perlin and libnoise to 6. Ridged multifractal (1 - |n|, with per-octave feedback weighting) is the standard mountain shaper; domain warping (fbm(p + 4·fbm(p))) costs 3 fBm evaluations per sample for one warp and 5 for two, and is what gives "non-square" organic coastlines and caves. Minecraft-style voxel terrain pairs a 2D fBm heightmap/splines with a 3D fBm density plus a vertical gradient bias.

### Cited Findings
- fBm: sum octaves with amplitude ∝ frequency^(-H); per-octave gain G = 2^-H, so H in [0,1] gives G in [1, 0.5]; G = 0.5 is the most common choice and many programmers use G directly without thinking of H — [Inigo Quilez, fBm](https://iquilezles.org/articles/fbm) (article content via search excerpts; the page itself 404'd for my fetcher)
- Red Blob's basic form: `1*noise(1x) + 0.5*noise(2x) + 0.25*noise(4x)`, divided by the amplitude sum (1.75) to renormalise; he often uses amplitudes [1, 1/2, 1/3, 1/4, 1/5] for more fine detail; redistribution `elevation = pow(e * fudge, exponent)` (fudge ≈ 1.2) pushes mid-values down into flatter lowlands; terraces via `round(e*n)/n` — [Red Blob Games](https://www.redblobgames.com/maps/terrain-from-noise/)
- Decorrelating octaves: use separate seeds per octave, or offset each octave's coordinates (e.g. `2*nx + 5.3`), or rotate some octaves; biome moisture and elevation noises must use different seeds "or the two maps will match" — [Red Blob Games](https://www.redblobgames.com/maps/terrain-from-noise/)
- FastNoiseLite fractal types: None, FBm, Ridged, PingPong, DomainWarpProgressive, DomainWarpIndependent (the two DomainWarp types only affect `DomainWarp()`); defaults octaves 3, lacunarity 2.0, gain 0.5, weighted_strength 0.0 (keep in 0..1), ping_pong_strength 2.0, frequency 0.01, seed 1337, domain_warp_amp 30.0 (C header; the wiki says amplitude default 1.0 — conflicting) — [FastNoiseLite wiki](https://github.com/Auburn/FastNoiseLite/wiki/Documentation); [C/FastNoiseLite.h](https://raw.githubusercontent.com/Auburn/FastNoiseLite/master/C/FastNoiseLite.h)
- stb_perlin suggests starting values of 6 octaves, lacunarity ≈ 2.0 (exactly 2.0 if you need wrapping), gain 0.5, ridge offset ≈ 1.0; it provides fbm, turbulence (sum of |octave|) and ridge variants, each calling base noise once per octave — [stb_perlin.h](https://github.com/nothings/stb/blob/master/stb_perlin.h)
- libnoise RidgedMulti defaults: frequency 1.0, lacunarity 2.0, octave count 6; ridged multifractal has no persistence setting, weighting comes from a per-octave feedback loop. libnoise Perlin docs recommend lacunarity 1.5-3.5 and persistence 0-1 — [libnoise RidgedMulti docs](https://libnoise.sourceforge.net/docs/classnoise_1_1module_1_1RidgedMulti.html); [Sponge noise RidgedMulti](https://jd.spongepowered.org/noise/2.0.0-SNAPSHOT/org.spongepowered.noise/org/spongepowered/noise/module/source/RidgedMulti.html); [libnoise Perlin docs](https://libnoise.sourceforge.net/docs/classnoise_1_1module_1_1Perlin.html)
- Rust `noise` crate Billow default: persistence 0.5, 6 octaves, frequency 1.0; the crate implements Fbm, Billow, RidgedMulti, HybridMulti, BasicMulti, Turbulence, Terrace, Curve — [docs.rs/noise Billow](https://docs.rs/noise/0.5.0/noise/struct.Billow.html); [docs.rs/noise](https://docs.rs/noise)
- Domain warping (IQ): f(p + h(p)) with both built from fBm. One warp: `q = (fbm(p), fbm(p + (5.2,1.3)))`, result `fbm(p + 4.0*q)`. Two warps: `r = (fbm(p + 4q + (1.7,9.2)), fbm(p + 4q + (8.3,2.8)))`, result `fbm(p + 4.0*r)`; the offsets "have no special meaning". Count (derived from the code): 1 warp = 3 fBm evaluations, 2 warps = 5 — [Inigo Quilez, Warping](https://iquilezles.org/articles/warp)
- FastNoise2 node types include fractals FBm and Ridged; domain warps Gradient, Simplex, SuperSimplex, Fractal Progressive, Fractal Independent; modifiers Remap, Terrace, Domain Scale/Offset/Rotate; v1.0.0 added PingPong, Abs, Modulus, DomainRotatePlane nodes — [FastNoise2 README](https://github.com/Auburn/FastNoise2); [FastNoise2 releases](https://github.com/Auburn/FastNoise2/releases)
- Minecraft noise definitions are fBm configurations with `base_octave` (formerly `firstOctave`), `octave_count` (1-32), `base_amplitude`, optional per-octave `amplitude_modifiers`, and `normalize`; output "approximates a normal distribution" — [minecraft.wiki Custom noise](https://minecraft.wiki/w/Custom_noise)
- Minecraft terrain blends two fractal maps with different parameters using a third noise map; 1.18 uses "over 50" noise maps; climate noises temperature, humidity, continentalness, erosion, weirdness drive biome choice, and splines on continentalness/erosion/peaks-and-valleys/weirdness drive terrain offset and jaggedness — [Alan Zucconi](https://www.alanzucconi.com/2022/06/05/minecraft-world-generation/); [minecraft.wiki Custom world generation tutorial](https://minecraft.wiki/w/Tutorial%3ACustom_world_generation)
- Minecraft `spline` density function: cubic spline over a `coordinate` density function with points (location, value, derivative); `gradient` (formerly `y_clamped_gradient`) maps Y linearly between from/to values — the vertical density bias — [minecraft.wiki Density function](https://minecraft.wiki/w/Density_function)
- Worley F2-F1 is low at cell boundaries (edge emphasis); cellular noise is listed as good for "plateaus, mesas, biome borders, cracked terrain" — [shader-noise reference](https://skillselion.com/skills/bbeierle12/skill-mcp-claude/shader-noise); [World Creator noise reference](https://docs.world-creator.com/reference/terrain/noises)

### Inferences
- For a 32x32 heightmap, 4-6 octaves of 2D noise is cheap (1024 samples × 6 octaves × ~10-14 ns ≈ 60-90 µs scalar); octaves beyond the point where wavelength < 1 block add only aliasing. For 3D density, 3-4 octaves is the usual budget (see performance section).
- Pairings that match voxel terrain: 2D fBm (or ridged for mountain biomes) → height; 3D fBm density + Y gradient (Minecraft "squashing") → overhangs/caves; ridged on 2S for mountain crests; |noise| thresholds ("spaghetti" = two ridged 3D noises both near zero) for tunnels; domain warp on the 2D control noises (continentalness) for non-square coastlines. The first three are directly supported by stb_perlin/FastNoiseLite; the others are a few lines on top.
- Ping-pong (FastNoiseLite) is a "banded/terraced" fractal; its documented default strength 2.0 and lack of coverage elsewhere suggest it is a niche effect rather than a terrain staple.

### Gaps
- IQ's fBm article content was only available via search excerpts; octave-count recommendations and terrain-H remarks could not be verified verbatim.
- No source quantifies hybrid multifractal parameters (Musgrave's offset/H) in a 2025-current library other than the Rust `noise` crate's existence of `HybridMulti`.
- The exact Minecraft octave lists (firstOctave/amplitudes) for continentalness/erosion were not on the wiki page I could fetch; the page points to misode.github.io's noise generator.

## Libraries: FastNoiseLite, FastNoise2, libnoise, stb_perlin.h, OpenSimplex2, FastNoiseSIMD, Rust crates

### Takeaway
Two libraries are directly linkable from a C FFI without a C++ toolchain: **FastNoiseLite** (single header `C/FastNoiseLite.h`, MIT, v1.1.1 March 2024, implements OpenSimplex2/2S, Perlin, Value, Value-Cubic, Cellular, fBm/ridged/ping-pong, domain warp, 3D rotation) and **stb_perlin.h** (single header, MIT/Unlicense, 3D Perlin + fbm/turbulence/ridge, 8-bit seed). **FastNoise2** has an official plain-C API (`FastNoise_C.h`) with SIMD batch generation (5-8x faster) but must be built with CMake/C++17 and linked as a shared/static library. libnoise is LGPL-2.1 C++ from 2003-2005 with no C API and no maintained upstream. OpenSimplex2's repo has no plain-C reference, but its Rust build exports a C FFI and FastNoiseLite's C port implements the algorithm.

### Inferences
- FFI difficulty ranking: stb_perlin.h and FastNoiseLite C = trivial (compile one .c with `FNL_IMPL`, call three functions; the state struct is plain data so March could even fill it directly). OpenSimplex2 = port the Java/C# reference (~300 lines) or use FastNoiseLite's C implementation.
- FastNoiseLite's C header is the single most complete option for this engine: it covers every noise type and fractal in the question except hybrid multifractal and billow (billow is `|n|`-style and trivial to add; ridged is included).
- Since FastNoiseLite v1.1.0 deliberately changed hashing/jitter constants between versions, pin the header version if world seeds must be stable across engine upgrades.

## Cellular / Worley noise and its uses

### Takeaway
Cellular (Worley/Voronoi) noise is the most expensive primitive (≈ 5x value noise in 3D, ≈ 80 ns scalar / 19 ns AVX2 per 3D sample) but is the natural tool for cell-shaped regions (biome patches, rock/crack patterns via F2-F1) and blob caves (F1 threshold). FastNoiseLite's C header provides all common distance metrics and return types including CellValue (per-cell id) and Distance2Sub (F2-F1).

### Cited Findings
- Worley noise (1996) = Voronoi/cellular noise; F1 = distance to nearest feature point, F2 = second nearest; F2-F1 is low at cell boundaries, useful for edge emphasis — [Wikipedia, Worley noise](https://en.wikipedia.org/wiki/Worley_noise); [shader-noise reference](https://skillselion.com/skills/bbeierle12/skill-mcp-claude/shader-noise)
- FastNoiseLite cellular: distance Euclidean/EuclideanSq (default)/Manhattan/Hybrid; return CellValue, Distance (default), Distance2, Distance2Add/Sub/Mul/Div; jitter 1.0, >1 causes artefacts — [FastNoiseLite wiki](https://github.com/Auburn/FastNoiseLite/wiki/Documentation)
- FastNoise2 cellular nodes: Cellular Value, Cellular Distance, Cellular Lookup (sample another noise per cell) — [FastNoise2 README](https://github.com/Auburn/FastNoise2)
- Cost: 3D cellular 12.49 Mpts/s scalar vs 64.13 value; 52.43 Mpts/s AVX2 — [FastNoiseLite README](https://github.com/Auburn/FastNoiseLite); [FastNoise2 README](https://github.com/Auburn/FastNoise2)
- Cave uses: a voxel carver samples "seeded 3D Worley F1/F3-edge cellular noise warped by a 2D Perlin displacement field"; another treats a voxel as air when distance-to-air-seed + Perlin < distance-to-solid; forum: Worley "is a bunch of combined spherical cells, which is great for making small spherical rooms"; advice to use the same cave function across all biomes so caves stay seamless at biome borders — [roxlap-cavegen](https://docs.rs/roxlap-cavegen/0.1.1/src/roxlap_cavegen/worley.rs.html); [Boundless forum](https://forum.playboundless.com/t/having-the-hardest-time-with-cave-noise/2664/2)
- Cellular noise listed as suited to plateaus, mesas, biome borders, cracked terrain; "F2-F1" produces bumps/scales — [World Creator docs](https://docs.world-creator.com/reference/terrain/noises); [shader-noise reference](https://skillselion.com/skills/bbeierle12/skill-mcp-claude/shader-noise)

### Inferences
- CellValue mode returns a constant per cell, i.e. a cheap seeded region id — directly usable as a biome/region lookup; domain-warp the input first to break the polygonal look.
- For blob caves, 3D F1 thresholded (F1 < r) gives rounded chambers; 2D cellular at a low frequency gives rock-plate patterns on surfaces. Keep cellular to 1 octave given its cost.

### Gaps
- No source quantified Minecraft's use of cellular noise (its caves use thresholds on fractal noise, per Zucconi), so the "cell-like biome regions" use is an inference from the properties, not from a shipped voxel game.

## Hashing for seeded lattice noise

### Takeaway
Three well-documented integer hashes fit lattice noise: PCG (RXS-M-XS, 32-bit, one multiply-add + shift-xor + multiply + xor; "should probably be your default"), SquirrelNoise5 (Eiserloh's noise-based RNG, CC-BY-3.0, fixes a repetition weakness in Squirrel3), and FastNoiseLite's prime-per-axis XOR + single multiply. Mixing axes with large distinct primes and injecting the seed before the avalanche steps avoids seed/axis correlation; seeding each octave differently (seed+octave or coordinate offsets) avoids octave correlation.

### Cited Findings
- PCG hash: `state = in*747796405u + 2891336453u; word = ((state >> ((state>>28u)+4u)) ^ state) * 277803737u; return (word>>22u) ^ word;` — in Jarzynski & Olano's tests PCG dominates the Wang hash, is "one of the best balanced choices between performance and quality overall", "slightly better performance and much better statistical quality than the Wang hash", and the author says it "should probably be your default GPU hash function"; the paper also introduces multi-dimensional pcg3d/pcg4d hashes — [Nathan Reed, Hash Functions for GPU Rendering](https://reedbeta.com/blog/hash-functions-for-gpu-rendering/); [Jarzynski & Olano, JCGT 2020](https://www.jcgt.org/published/0009/03/02/paper.pdf)
- SquirrelNoise5 (Eiserloh): `m = (uint)pos * 0xd2a80a3f; m += seed; m ^= m>>9; m += 0xa884f197; m ^= m>>11; m *= 0x6C736F4B; m ^= m>>13; m += 0xB79F3ABB; m ^= m>>15; m *= 0x1b56c4f5; m ^= m>>17;` 2D index = x + 198491317*y; 3D adds 6542989*z; 4D adds 357239*t; CC-BY-3.0 US, attribution in source comments suffices; author's note that it is work in progress / not all functions tested — [kevinmoran gist of SquirrelNoise5](https://gist.github.com/kevinmoran/0198d8e9de0da7057abe8b8b34d50f86)
- The GDC 2017 talk "Math for Game Programmers: Noise-Based RNG" presented Squirrel3; Eiserloh later credited Peter Schmidt-Nielsen with finding a weakness (noise repetition at extremely high position values) fixed in SquirrelNoise5; a Swift port found the C version 4x faster than the Swift one — [annardunster blog](https://annardunster-lhli5hya9-ardunsters-projects.vercel.app/posts/2024/eiserloh-noise-rng-rust); [maartene blog](https://maartene.github.io/blog/files/4550a51525c9c2a44d04ac24761e9f71-24.html)
- FastNoiseLite hash: `(seed ^ (x*501125321) ^ (y*1136930381) ^ (z*1720413743)) * 0x27d4eb2d`, then shifted/masked to select gradient — [C/FastNoiseLite.h](https://raw.githubusercontent.com/Auburn/FastNoiseLite/master/C/FastNoiseLite.h)
- stb_perlin uses a 256-entry permutation table (hence period 256) and only 8 seed bits — [stb_perlin.h](https://github.com/nothings/stb/blob/master/stb_perlin.h)
- Decorrelating octaves: separate seeds per octave or per-octave coordinate offsets/rotations — [Red Blob Games](https://www.redblobgames.com/maps/terrain-from-noise/)
- Adjacent lattice points receiving similar gradients cause visible correlation in Perlin noise; the 2001 "Noise Hardware" fix is a better gradient set and hashing — [Perlin, Noise Hardware](https://userpages.cs.umbc.edu/olano/s2001c24/ch09.html)

### Inferences
- The engine's "hash of lattice points" should be checked against two failure modes the sources name: (a) a tiny-period permutation table (stb-style 256) that visibly tiles at large coordinates; (b) axis mixing by small multipliers, which creates diagonal correlation. A FastNoiseLite-style prime-per-axis XOR followed by a PCG or Squirrel5 avalanche is cheap (≈ 5-10 integer ops) and avoids both.
- Mixing the seed in with XOR before the multiply (FastNoiseLite) means seed s and s^k for small k produce related lattices; adding the octave index to the seed and then running a full avalanche (Squirrel5 style) gives better octave independence than XOR alone. (Inference from the hash structures above, not benchmarked.)

### Gaps
- No source gave measured avalanche/statistical quality for FastNoiseLite's hash or Squirrel5 comparable to the Jarzynski-Olano Pareto tests; only PCG has published quality numbers.
- I could not retrieve the GDC talk itself (video), only secondary write-ups.

## Determinism and seeding: 32 vs 64-bit, float reproducibility, chunk-local evaluation

### Takeaway
Lattice noise is inherently chunk-local: each sample depends only on the hash of nearby lattice points, so any chunk can be generated without neighbours (the Minecraft density pipeline and FastNoise2's offset+count grid API are built on this). Bit-exact cross-platform reproduction of float noise requires disabling FMA contraction and fast-math, avoiding x87 extended precision and libm transcendentals, and testing on at least two architectures; integer/fixed-point hashing of lattice points is the part that is trivially portable. All surveyed C libraries use 32-bit int seeds (FastNoiseLite 1337 default, stb_perlin 8 bits); Minecraft's data format keeps a `legacy_random_source` flag, showing that changing the RNG breaks seed compatibility.

### Cited Findings
- FMA rounds once across an expression so it must be turned off for cross-platform determinism: Clang/GCC `-ffp-contract=off`, MSVC `/fp:strict`; Box2D also had to avoid fast-math and write its own `atan2f`; `sqrt` is deterministic on x64 (SSE `sqrtss`) — [Box2D determinism post](https://box2d.org/posts/2024/08/determinism/); [yomotherboard x86 vs ARM64](https://yomotherboard.com/?p=536957)
- x87 80-bit intermediates change results; libm `sin/cos/exp` differ between platforms; IEEE add/mul/div are exactly rounded when the compiler does not reorder or fuse; a CI matrix with at least two architectures is recommended; integer/fixed-point avoids the problem entirely — [bugnet.io](https://bugnet.io/blog/how-to-debug-floating-point-determinism-across-platforms); [Gaffer on Games, Floating Point Determinism](https://new.gafferongames.com/post/floating_point_determinism/)
- FastNoiseLite: `int seed` default 1337; `FNLfloat` selectable float/double; v1.1.0 changed hashing in JS and jitter constants so output differs from v1.0.1 "even with matching seeds" — [FastNoiseLite wiki](https://github.com/Auburn/FastNoiseLite/wiki/Documentation); [releases](https://github.com/Auburn/FastNoiseLite/releases)
- stb_perlin: only the bottom 8 bits of the seed are used — [stb_perlin.h](https://github.com/nothings/stb/blob/master/stb_perlin.h)
- Minecraft noise JSON has `legacy_random_source` (when true, `base_octave` must be ≤ 1), i.e. two RNG back-ends coexist for seed compatibility — [minecraft.wiki Custom noise](https://minecraft.wiki/w/Custom_noise)
- FastNoise2 generates by (offset, count, step) grid per call, with seed passed per call and `GenPositionArray` for scattered positions — [FastNoise_C.h](https://raw.githubusercontent.com/Auburn/FastNoise2/master/include/FastNoise/FastNoise_C.h)
- Minecraft `interpolated` cells and `flat_cache` (once per 4x4 column at Y=0) / `cache_2d` (once per horizontal position) / `cache` (once per block position when referenced twice) are per-chunk evaluation caches; cell size = size_horizontal*4 by size_vertical*4 blocks — [minecraft.wiki Density function](https://minecraft.wiki/w/Density_function)
- Eiserloh's noise-RNG model: a position+seed hash behaves "as if it is an endless, stateless table of possibilities", so results are order-independent — [annardunster blog](https://annardunster-lhli5hya9-ardunsters-projects.vercel.app/posts/2024/eiserloh-noise-rng-rust)

### Inferences
- 32-bit vs 64-bit: all surveyed C-callable libraries take a 32-bit seed; a 64-bit world seed can be folded to per-noise 32-bit seeds with a PCG/Squirrel5 step (seed64 → hash(lo ^ hi ^ noise_id)). None of the sources address 64-bit lattice coordinates; with `float` inputs, precision near |x| > 2^23 blocks degrades, so sample in chunk-local coordinates plus a double or integer chunk origin. (Inference; no source gave a concrete threshold for noise specifically.)
- Chunk-local evaluation is free for lattice/simplex/cellular noise; only cross-chunk features (rivers, structures) need neighbour queries, which is a higher-level design concern outside this note.
- If March's compiler or the C toolchain may fuse multiply-adds differently per platform, world files should store the generator version and the engine should run a golden-image test (fixed seed → hash of a 32^3 density field) on each supported architecture.

### Gaps
- No source directly discusses float-vs-double trade-offs for noise at large world coordinates; the threshold above is my inference from IEEE single precision.
- No source documents FastNoiseLite's behaviour under `-ffp-contract` differences; whether its outputs are bit-identical across x86/ARM is untested in the material I found.

## Performance: per-sample cost, SIMD batches, per-chunk budgets, low-resolution density interpolation

### Takeaway
Scalar OpenSimplex2 costs ≈ 27 ns per 3D sample and ≈ 14 ns per 2D sample on a 4.9 GHz desktop core; FastNoise2 AVX2 brings 3D simplex to ≈ 3.7 ns. A full 32x32x32 density field at 3 octaves is therefore ≈ 2.7 ms scalar or ≈ 0.4 ms SIMD per chunk, versus ≈ 40 µs for a 32x32 heightmap at 3 octaves. Minecraft's approach — sample density on a 4x8x4-block cell grid and trilinearly interpolate — reduces 3D samples by ~80x for a 32^3 chunk, at the cost of visibly "square" hills that it compensates for with extra depth noise.

### Cited Findings
- FastNoiseLite scalar (Intel 7820X @ 4.9 GHz, clang-cl /O2) Mpts/s: 2D Value 114.01 / Perlin 92.83 / Simplex 71.30 / Cellular 39.15; 3D Value 64.13 / Perlin 47.93 / Simplex 36.83 / Cellular 12.49 — [FastNoiseLite README](https://github.com/Auburn/FastNoiseLite)
- FastNoise2 AVX2 Mpts/s: 2D Value 776.33 / Perlin 624.27 / Simplex 466.03 / Cellular 194.30; 3D Value 494.49 / Perlin 261.10 / Simplex 268.44 / Cellular 52.43; legacy FastNoise (scalar) 3D Value 49.34 / Perlin 37.75 / Simplex 44.74 / Cellular 13.27 — [FastNoise2 README](https://github.com/Auburn/FastNoise2)
- FastNoise2 `fnGenSingle*` is documented as "very slow"; grid and position-array calls are the intended batch path; avoid `xCount = 1` slices — [FastNoise_C.h](https://raw.githubusercontent.com/Auburn/FastNoise2/master/include/FastNoise/FastNoise_C.h)
- Each fractal octave is one base-noise call, so cost scales linearly with octave count — [stb_perlin.h](https://github.com/nothings/stb/blob/master/stb_perlin.h)
- Minecraft interpolation: cell size is `size_horizontal*4` by `size_vertical*4` blocks; overworld preset size_horizontal 1, size_vertical 2 → 4-wide, 8-tall cells; valid 0-4, value 0 crashes (divide by zero), value 3 gives 12-block cells that do not tile 16-block chunks — [minecraft.wiki Density function](https://minecraft.wiki/w/Density_function); [Fandom Custom page](https://minecraft.fandom.com/wiki/Custom); [MC-185156](https://bugs-legacy.mojang.com/browse/MC-185156); [misode gist thread](https://gist.icoder.workers.dev/misode/b83bfe4964e6bf53b2dd31b22ee94157)
- Zucconi: Minecraft splits the world into cells of 4x8x4 blocks, samples fractal noise at cell corners and interpolates "for performance"; the smoothing removes fine detail, which a separate "depth noise" map compensates; climate noises are sampled per quarter-chunk (4x4x4) — [Alan Zucconi](https://www.alanzucconi.com/2022/06/05/minecraft-world-generation/)
- Notch's 2011 description: coarse density grid with linear interpolation, spacing 8 blocks horizontally and 4 vertically (older generator; differs from the modern 4x8x4) — [Notch on ModDB, Terrain generation part 1](https://www.moddb.com/news/terrain-generation-part-1)
- Independent lerp3 benchmark (Rust, simdnoise, 8x8x8 → 16x16x16): direct 16^3 generation 113,810 ns; naive trilinear lerp 114,564 ns (no gain); refactored lerp 95,697 ns; precomputed t-values with interpolation 89,285 ns (≈ 22% faster than direct); skipping lerp when t = 0 was 14% slower; the interpolation makes hills "square and blocky" — [saskapult, 3D Noise Scaling](https://saskapult.github.io/blog/lerp3)
- Minecraft evaluation caches: `flat_cache` once per 4x4 column at Y=0, `cache_2d` once per XZ, `cache` once per block when referenced twice; `interpolated` is being replaced by `upscale` in 26.4 — [minecraft.wiki Density function](https://minecraft.wiki/w/Density_function)
- Minecraft density function also has `xz_scale`/`y_scale` on `noise`; `"xz_scale": 0.5` makes terrain smoother — [minecraft.wiki Noise router](https://minecraft.wiki/w/Noise_router)

### Inferences
- Per-chunk budget (derived from the FastNoiseLite scalar table, single core): 32x32 heightmap × 3 octaves OpenSimplex2 2D ≈ 1024 × 3 × 14 ns ≈ 43 µs; same with value noise ≈ 27 µs. 32^3 density × 3 octaves OpenSimplex2 3D ≈ 32768 × 3 × 27 ns ≈ 2.7 ms; value noise ≈ 1.5 ms; cellular 1 octave ≈ 2.6 ms. With FastNoise2 AVX2: 32^3 × 3 × 3.7 ns ≈ 0.36 ms.
- Minecraft-style 4x8x4 cells on a 32^3 chunk need (32/4+1) × (32/8+1) × (32/4+1) = 405 corner samples instead of 32,768 (≈ 81x fewer); the trilinear fill is ~7 lerps per voxel. The lerp3 benchmark shows the interpolation itself is not free: only a well-written lerp (precomputed t, no divisions) beat direct generation at a 2x factor; at 4x/8x factors the savings are far larger (not benchmarked in the source).
- A sensible layering for the engine: cheap 2D control noises cached per column (`cache_2d`/`flat_cache` idea), 3D density sampled on a coarse cell grid and interpolated, and only the final octave (if any) sampled per voxel for detail. FastNoiseLite scalar is enough for this budget on a worker thread; FastNoise2 is the upgrade path if full-resolution 3D density is wanted.

### Gaps
- No published FastNoiseLite benchmark for the C99 port specifically (the table is C++); the C code is a straight port so similar numbers are expected but unverified.
- No source gave ns/sample for domain warp or for OpenSimplex2S; FastNoise2's asterisk on the OpenSimplex figure is unexplained.
- The exact modern Minecraft noise sampling octave counts per noise (e.g. continentalness `firstOctave -9`, 9 amplitudes) could not be fetched from the wiki page; misode's noise tool holds the data.
